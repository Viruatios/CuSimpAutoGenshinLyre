# 简化自动原琴 - CuSimpAutoGenshinLyre

一个BetterGI的JS自动化脚本，从提瓦特钓鱼玳师和半江残秋老师的AutoYuanQin简化修改而来。

## 播放演奏脚本

1. 在全自动 - 调度器中 新建配置组/选择已有的组 将*CuSimpAutoGenshinLyre*添加至配置组中
2. 右键原琴 - 修改脚本自定义配置 按照说明填写
3. 点击运行开始播放音乐

## 曲谱文件位置

1. 所有的曲谱文件应放置于 `CuSimpAutoGenshinLyre/assets/score_file` 路径下

## 文件结构

一个标准的曲谱.json文件的基本结构如下(五线谱制谱器/简谱制谱器格式)：

```json
{
	"name": "",
	"author": "",
	"instrument": "",
	"description": "",
	"type": "",
	"bpm": "",
	"time_signature": "",
	"composer": "",
	"arranger": "",
	"notes": ""
}
```

**注意**：以上代码中仅 : 右侧的**双引号内**的部分可以更改, 具体的曲谱格式请参考 `/assets/tutorial_file` 路径下的 `000X.歌曲名.json`

### 字段说明

`name`: **必要键值** 曲谱名

`author`: **可选键值** 录谱人, 制作这个.json曲谱的作者名

`instrument`: **可选键值** 此键值对用于建议用户的乐器使用

`description`: **可选键值** 可以随意填写关于该曲谱的描述信息

`type`: **必要键值** 决定曲谱的解析方式, 固定为`keyboard`(你在网上看到的键盘琴谱格式与此相似)

`bpm`: **必要键值** 曲谱的BPM (Beats Per Minute)

`time_signature`: **必要键值** 拍号, 例如 3/4 代表 以四分音符为一拍每小节三拍(被设为一拍的音符仅支持2的幂)

`composer`: **可选键值** 曲师

`arranger`: **可选键值** 谱师

`notes`: **必要键值** 曲谱内容,该部分如何解读请参考下文中修改后的[读谱规则](#v010-修改后的读谱规则)

### 代码美化

曲谱JSON文件的"notes"的值视作一个字符串, 在这个字符串内仅可以使用**换行符**美化代码, 通过这种方法可以使用记事本等软件从.json文件中获取带有换行的曲谱代码(**notes内的换行符不会被读取执行**，所以不用担心多加的换行符会影响脚本读取)

# 更新日志

## v0.1.x 主要改动：读谱规则极度简化。以及播放调度模型的修改。

### v0.1.0 修改后的读谱规则

1. 只对于“点按弹奏琴”有效，只对于“键盘谱”有效。不支持其他类型。
2. 定义：每个音符为一个基本单位，它可能是“休止符”、“单个按键”、“同时按下按键”或是“琶音按键”。
3. 定义：“空格”和“/”都是“停止符”，表示位于该符号前面的音符演奏到这里停止。其中 “空格” 是 “基本单位的停止符”，而 “/” 是 “一拍的停止符”。
4. 定义：单行之中的按键视作一小节，即不同小节之间以“\n”分割。
5. 规定：一拍的时长由BPM决定；每一拍内的“基本单位”均分这一拍的时长。
6. 规定：对于每一拍内，只有上一个“基本单位”的持续时长结束，才能演奏下一个“基本单位”。该等待规则不仅作用于每一拍之间，也作用于每个“基本单位”之间。
7. 规定：对于每个“基本单位”，单个字母视作“单个按键”，一个“()”内的所有字母视作“同时按下按键”，多个字母则视作“琶音按键”。
8. 约定：“基本单位”也可以是一个“休止符”，“休止符”在谱序列中不占位置。例如，谱序列“空格 A 空格 B 空格 空格 /”，被解读为“休止符+音符A+音符B+休止符+这一拍结束”。
9. 约定：在“/”之前不允许具有“休止符”，因此“休止符”只能存在于“空格停止符”之前。此外，由于每小节基本以拍为单位，因此实际操作上忽略“\n”的停止符作用。
10. 约定：对于“琶音按键”内的多个字母按键，每个字母按键均分该“琶音按键”的时长。
11. 约定：“琶音按键”是一个特殊的“基本单位”，其中也允许存在“同时按下按键”和“单个按键”的混合，演奏时按照它们各自的演奏规则进行。例如“(AB)C(DE)”是一个“琶音按键”，其中包含了一个“同时按下按键”(AB)，一个“单个按键”C和另一个“同时按下按键”(DE)。

### v0.1.1 对播放调度模型的修改

原模型为何不符合规则6：

1. 对每个音符调用一次异步 notePlay，但不等待它结束。这样“下一个基本单位必须等上一个基本单位结束”只靠 offset 间接实现，不是强约束。只要计时抖动或调度顺序变化，就可能出现时值不符合预期。
2. 两个协程都在操作同一个键。例如前一单位末尾 keyup 与下一单位开头 keydown 在同一时间点附近触发时，若前一单位的 keyup 晚到，会把下一单位刚按下的键立即抬起，导致后一个单位实际时长变短。
3. wait 和 time 都做 Math.floor，单位越细（例如一拍内分得越多），累计截断误差越明显。结果是“单位结束时间”会早于理论值，听感上就是持续时长不准。
4. 结论：核心的问题在播放调度模型：当前是“按音符并发定时”，不是“按基本单位串行执行”。这会直接破坏“上一个基本单位结束后再进入下一个”的强等待规则。解析侧（offset、unitDuration）大体是对的，但会被并发竞态和取整误差放大。

改动：

1. 序列化结构升级为“基本单位序列”

- `keySheetSerialization` 现在输出：`[小节拍数, ...基本单位]`。
- 基本单位结构为：`{ kind: rest|single|chord|arpeggio, keys: string[], time: number }`。
- 这使播放层可以直接按单位串行执行，不再依赖“按音符并发 + offset”间接对齐。

2. 播放调度模型重构为单位时间轴串行驱动

- 每个基本单位执行前必须等待到其开始时刻，执行完成后才进入下一个单位。
- 调度使用 `await` 串行推进，从根上保证“上一个单位结束后再进入下一个单位”。
- 同键位的 `keyup/keydown` 竞态被消除，避免单位边界误抬键导致时值缩短。

3. 时值对齐策略调整

- 改为基于绝对时间点对齐（`sleepUntil`）并使用 `Math.round`，降低累积截断误差。
- 每小节结束会对齐到理论小节终点，减少长曲播放漂移。

4. 行为结果

- 串行、和弦、琶音与休止符都在同一时间轴模型下执行，时值一致性更高。

### v0.1.2 读谱细节优化

- 如果一拍的内容编写为 "A B /"（注意 B 后面有一个用于排版的空格），按 / 首先被分割为 "A B "（末尾多一个空格）。
  当对 "A B " 执行 .split(' ') 时，会被分割为 ["A", "B", ""]。此时 units.length 变成了 3（而不是预期的 2），多出来的 "" 触发了定义的“两个空格之间视为休止符”的逻辑。这导致原本各占 1/2 拍的 A 和 B，变成了各占 1/3拍，并在结尾多出了 1/3拍的休止符。
- 通过将每一拍的字符串在切割前进行 .trim()（去除头尾排版多余空格）解决了该问题。不仅去除了该副作用，而且仍然完美支持内部连续空格（例如 "A B" 中间连续两个空格）产生休止符的逻辑。

### v0.1.3 按键细节优化

- 当出现两个相同的连续基本按键（例如 A 后面紧跟着还是 A）时：

  第一拍结尾处，代码执行 keyUp('A') 抬起按键。
  JS 是单线程的，代码在一两毫秒内就迅速走完了对下一拍按键时间的计算并回到这里，直接执行下一拍的 keyDown('A')。
  两次操作之间的真实物理时间几乎为0（小于1-2毫秒）。
  原神等相当一部分游戏的引擎，是通过循环轮询（如以60Hz，即大约每16毫秒轮询一次）来检测输入状态的。在这样一次微小得连一帧都不到的过程中，按键状态经历了“按下 -> 抬起 -> 再次按下”。对于引擎来说，因为状态变化太快，它根本没捕捉到“抬起”这个动作，也就不会产生第二次“按下”的独立事件，最终导致相同的后续按键就像“被跳过了”一样，俗称**“吞键”**。

- 解决：在每一个演奏方法中添加了自动“提前抬键以切断连音”的机制：

  通过强制让每个音符在结束前留出约15毫秒的物理抬键空隙，就可以保证游戏引擎能切实地识别到前一个键已经“弹起”，进而完美触发后续重复的“基本单位”这个问题。这一修改也完全生效于和弦与琶音按键中。

### v0.1.4 增加并落实琶音按键的解析规则

- 改进了底层按键的解析方式（正则分割）：
  弃用了之前过于简单而容易导致逻辑冲突的 startsWith 判断，改用正则表达式 /\([A-Za-z]+\)|[A-Za-z]/g 将形如 (AB)C(DE) 的复杂基本单位精确切分成不同的原子块 —— 即 ["(AB)", "C", "(DE)"]。
  这样该特殊的琶音按键会被存储成一个两级数组的形式 [['A','B'], ['C'], ['D','E']] 用于后续播放。

- 改进了执行器 unitPlay 中的遍历触发器：
  在 if (unit.kind === "arpeggio") 分支的循环调度中，兼容了这种嵌套数组写法（对原单纯的单音琶音也能自动向后兼容为数组）。由于同一块内可能存在多个待触发的按键，我在计算好每一等分的 StartTime 之后，将直接使用 for (const key of keyGroup) 同时 keyDown 块内的所有按键（如同时触发 A 和 B），等待单块时长结束后，再同时调用 keyUp 抬起所有按键，最后再衔接进下一个等分块中进行同样的操作。

现在，像如 (AB)C(DE) 之类的复杂排版单位将可以严密地先均分总时长，并在各自被分配的一等分时间内按上述规则准确演奏。

### v0.1.5 分隔符改用“-”

- 将规则中的分割符从“空格”修改为“-”，以避免与排版空格产生冲突。这是因为在之前的版本中，使用空格作为分隔符导致了诸如 "A B /" 这类情况的解析错误（末尾多一个空格导致多出一个空字符串，从而引入了意外的休止符）。改用“-”后，用户可以自由使用空格进行排版美化，而不会影响实际的音符解析和时值计算。

### v0.1.6 对读谱规则进行重大修改，重定义部分概念，撤销v0.1.2和v0.1.5（重要）

- v0.1.0中将“空格”和“/”错误地定义为“属于两段基本单位之间的分割”，导致了诸如 " A B /" 这类情况的解析错误（末尾多一个空格导致多出一个空字符串，从而引入了意外的休止符；v0.1.2又导致了开头的休止符无法被识别）。因此在v0.1.6中对读谱规则进行了重新定义和细化，明确了“空格”和“/”的作用和限制，以避免类似问题的发生。同时撤销了v0.1.2和v0.1.5中对分隔符和空格处理的修改，回归到更为简洁和直观的读谱方式。
- 新定义：
  1. “空格”和“/”都是“停止符”，表示位于该符号前面的音符演奏到这里停止。其中 “空格” 是 “基本单位的停止符”，而 “/” 是 “一拍的停止符”。
  2. “基本单位”也可以是一个“休止符”，“休止符”在谱序列中不占位置。
  3. 约定：在“/”之前不允许具有“休止符”，因此“休止符”只能存在于“空格停止符”之前。例如，谱序列“ A B /”，被解读为“休止符+音符A+休止符+音符B+这一拍结束”。

### v0.1.7 非四分音符节拍支持

- 在音乐中，BPM（Beats Per Minute） 大多默认以 四分音符（1/4 拍） 作为一拍的时间基准的。当谱子是 4/4 拍时，分母为 4（即四分音符），那么每拍的时长就是 60000 / BPM 毫秒，当前代码在这个基础上运算完美。但是，当遇到 6/8 拍的乐谱时，它的分母为 8（基础节拍是八分音符）。此时一个 / 之间表示的是一个八分音符，如果在代码中仍然强行把它当作四分音符计算时长（60000 / BPM），它的时间实际上只给了一半，这就会导致实际运行起来仿佛上了两倍速一样，产生异常加快。
- 通过加入对于 time_signature 拍号分母因子的自适应解析，当遇到例如 4/8 等非四分音符基底的拍号时，将会自动对 gap（每一拍的时长）乘以 (分母 / 4)（即对于 4/8 源分母 8，将 gap 时间翻倍 8/4 = 2）以修正速度过快的问题。

#### v0.1.7b 复合拍子（如 6/8 拍）节拍支持修正

- 修复了 v0.1.7 中处理 `6/8` 等拍号时演奏速度异常变慢的问题。在音乐理论中，对于分子能被 3 整除的八分拍（如 `6/8`、`9/8` 等“复合拍子”），其基本物理节拍单位并非单纯的“八分音符”或“两个四分音符”，而是**附点四分音符**（即 1.5 个四分音符）。
- 之前的版本中将 6/8 拍的一拍强行拉长到了两个四分音符的时值（乘以 `8/4 = 2.0` 倍数），导致播放实际速度慢了约 33%。
- 新的修改重新加入了复合拍子的判定分支：当遇到分母为 8 且分子为 3 的倍数的复合拍号（如 `6/8`）时，将正确赋予它们 `1.5` 倍四分音符的时值乘数。其他常规拍号则按真实的数学比例正常缩放，确保曲谱的 BPM 最终在各个类型的拍号里都能以完美的预期原速进行演奏。

### v0.1.8 演奏功能优化

- 修复了 JS 脚本在 `settings.json` 中部分配置“看起来可填、实际不生效”的问题。

- 问题根因：
  1. 播放主循环没有严格区分“单次模式”和“循环模式”，导致单次模式也可能被循环次数参数影响。
  2. 队列配置解析不够严格：队列为空时没有正确按“默认全部播放”处理，序号匹配也存在误匹配风险。
  3. 定时启动与间隔参数缺少统一的容错与默认值策略，部分输入下会出现行为与配置不一致。

- 本次改动：
  1. 重构设置解析逻辑：统一解析并校验 `music_start`、`music_repeat`、`music_interval`、`repeat_interval`。
  2. 明确四种播放模式行为：
     - 单曲单次执行：只执行 1 轮。
     - 单曲循环：按循环次数执行，`music_repeat=0` 时无限循环。
     - 队列单次执行：队列仅执行 1 轮。
     - 队列循环：队列按循环次数执行，`music_repeat=0` 时无限循环。
  3. 修复队列规则：
     - `music_queue` 留空时，默认按本地曲谱顺序播放全部曲目。
     - 队列序号改为按四位前缀精确匹配（如 `1` 对应 `0001.*`），避免模糊匹配造成选曲错误。
  4. 修正间隔生效范围：
     - `music_interval` 仅在队列模式下生效，且只在“曲目与曲目之间”等待。
     - `repeat_interval` 仅在循环模式下、且下一轮确实会执行时等待。

- 修复结果：
  `settings.json` 中以下配置现已按预期生效：定时播放、单曲循环、演奏队列单次执行、演奏队列循环、队列内演奏间隔时间。
